## Context

The current Schwab file import uses `SchwabParser` which only implements `parse()` — the legacy pipeline. This diverges fundamentally from the IBKR path:

| | IBKR (current) | Schwab CSV (current) |
|---|---|---|
| Raw record layer | `BrokerRawTransaction` | none |
| Idempotency key | `"{user_id}:ibkr:{txId}"` | fragile 5-tuple dedup |
| Timestamp | full datetime w/ seconds | UTC midnight (date only) |
| PnL | FIFO-computed | always `None` |
| Aggregation | `aggregate_executions_fifo_with_sources()` | inside `parse()` |
| Corporate actions | yes | no |

This means the same trades imported from IBKR XML vs Schwab CSV can produce different results. The goal of this change is full **pipeline parity**: both brokers feed into the same broker-neutral FIFO aggregator via `BrokerRawTransactionCreate`, so identical trade data — regardless of source format — produces identical `Trade` rows.

Schwab's Individual Trader API returns transactions as JSON arrays with `transferItems` containing per-instrument details. The test fixture `tests/test_data/schwab/schwab_aggregation.json` uses a slightly simplified variant: a flat `transactionItem` object (single instrument per record) with `instruction` values `BUY`, `SELL`, `SELL_SHORT`, `BUY_TO_COVER`. Both formats must be supported.

The IBKR raw pipeline is the reference implementation: `parse_raw()` → `BrokerRawTransaction` → `LogicalExecution` → `aggregate_executions_fifo_with_sources()` → `Trade`. The `aggregator.py` module already operates on the broker-neutral `ExecutionLike` protocol — no changes needed there. Only the parser and factory need updating to put Schwab on the same path.

## Goals / Non-Goals

**Goals:**
- Parse Schwab JSON transaction files into `BrokerRawTransactionCreate` via `parse_raw()`
- Support both `transactionItem` (flat, test fixture format) and `transferItems` (Schwab API array format)
- Add `POST /api/v1/imports/schwab-json` REST endpoint that accepts a JSON body directly
- Change the upload endpoint to accept `.json` for Schwab accounts (alongside or replacing `.csv`)
- Restrict frontend file dialog `accept` to `.json` for Schwab accounts
- Achieve idempotent re-import via BRT PK `"{user_id}:schwab:{activityId}"`
- Pass integration test: import `schwab_aggregation.json`, verify FIFO-matched trade count and P&L
- Map all four Schwab instructions correctly to `direction` + `opening/closing` semantics

**Non-Goals:**
- Keep the Schwab CSV import path working — `SchwabParser` is deprecated and removed from the factory as part of this change
- Implement the live Schwab OAuth/REST API sync (that's `BrokerService._sync_schwab()`, separate path)
- Support non-TRADE transaction types (dividends, fees) in this change
- Multi-leg combo grouping by `orderId` (deferred — single-leg only in this iteration)
- Modify `aggregator.py` — it is already broker-neutral and requires no changes

## Decisions

### D1: New parser class + deprecate SchwabParser (CSV)

**Decision:** Create `SchwabJSONParser` in `backend/app/utils/parsers/schwab_json.py`. Remove `SchwabParser` from `factory.py`. The `schwab.py` file is left in place but is no longer reachable via the factory — it can be deleted in a follow-up cleanup once confirmed no other code imports it.

**Rationale:** `SchwabParser` uses the legacy `parse()` path with no BRT layer — it can never produce the same results as the IBKR pipeline for equivalent data. Keeping it in the factory creates ambiguity about which path Schwab accounts use. Removing it from the factory makes the routing unambiguous: Schwab accounts only accept `.json`. The upload endpoint rejects `.csv` for Schwab with a clear error message pointing to JSON.

**Alternative considered:** Keep CSV as fallback → rejected (two divergent pipelines for same broker defeats the pipeline-parity goal).

### D2: Support both transactionItem and transferItems

**Decision:** Parser first checks for `transactionItem` key (flat, test fixture format), then falls back to `transferItems` array (official Schwab API format). Only the first instrument in `transferItems` is used for single-leg equities.

**Rationale:** The test fixture uses `transactionItem` (as generated by the aggregation script). The real Schwab API uses `transferItems`. Both need to work.

### D3: Direction mapping from `instruction` field

| instruction     | direction | side    |
|-----------------|-----------|---------|
| `BUY`           | `LONG`    | opening |
| `SELL`          | `LONG`    | closing |
| `SELL_SHORT`    | `SHORT`   | opening |
| `BUY_TO_COVER`  | `SHORT`   | closing |

The `direction` on `BrokerRawTransactionCreate` follows the trade direction (LONG/SHORT), not the leg side. The FIFO aggregator uses `direction` to match opening/closing legs by symbol+direction.

### D4: Quantity sign convention

`BrokerRawTransactionCreate.quantity` is always positive. The FIFO aggregator and `LogicalExecution` pipeline expect positive quantities with direction encoded separately.

### D5: Commission extraction

Schwab JSON in the test fixture does not carry explicit commission fields. Commission = `Decimal("0")` by default. If `transferItems` contains a leg with `feeType` in `{COMMISSION, SEC_FEE, TAF_FEE}` and no instrument symbol, extract its `cost` as commission. This matches the real API behavior.

### D6: REST endpoint for direct JSON body import

**Decision:** Add `POST /api/v1/imports/schwab-json` that accepts `Content-Type: application/json` with a JSON array body, requires `account_id` as query parameter, and delegates to `ImportService.import_file()` with the JSON serialized back to bytes.

**Rationale:** Enables automated/scripted workflows without multipart form. The endpoint validates the account is of type `SCHWAB` before proceeding.

### D7: File accept restriction on frontend

Change the file input `accept` attribute for Schwab accounts from `".csv"` (or generic) to `".json"`. This is a UI-only guard — the backend validates the content-type independently.

### D8: BRT external ID format

`"{user_id}:schwab:{activityId}"` — consistent with IBKR pattern `"{user_id}:ibkr:{transactionID}"`. The `activityId` from the JSON is the unique Schwab activity identifier.

### D9: Pipeline parity — aggregator.py is broker-neutral, no changes needed

**Decision:** Do not modify `aggregator.py` or `ImportService`. The raw-data pipeline in `ImportService.import_file()` already branches on whether `parse_raw()` raises `NotImplementedError`. Once `SchwabJSONParser` implements `parse_raw()`, Schwab automatically enters the same code path as IBKR — no conditional logic needed.

**Rationale:** The `ExecutionLike` protocol in `aggregator.py` defines the contract: `symbol`, `direction`, `quantity`, `price`, `commission`, `executed_at`, `multiplier`. Both IBKR and Schwab data map cleanly to these fields. The aggregator has no knowledge of broker origin. Pipeline parity is a natural consequence of both parsers satisfying the same interface.

**Implication for identical data:** Given two files with the same trades (one IBKR XML, one Schwab JSON), after import both produce the same `Trade` rows with the same `pnl`, `entry_price`, `exit_price`, `direction`, and `quantity` — provided timestamps are equivalent and no broker-specific adjustments (splits, FX) differ.

## Risks / Trade-offs

- **Risk: `activityId` collision across accounts** → Mitigation: `user_id` is part of the BRT PK, and account scope is enforced at the service layer. Multiple Schwab accounts per user are handled correctly.
- **Risk: `netAmount` used as proxy for cost** → In the test fixture, `netAmount` includes the cash impact (negative for buys, positive for sells). The `price` and `amount` fields in `transactionItem` are the canonical source for price/quantity. `netAmount` is stored in `raw_data` for reference only.
- **Risk: JSON files may be large (thousands of records)** → Mitigation: Existing bulk_upsert batching in `BrokerRawTransactionRepository` handles this. No changes needed.
- **Risk: Schwab JSON has no explicit `currency` field per transaction** → Default to `"USD"` (all Schwab domestic accounts are USD). Stored in `raw_data` for future FX support.

## Migration Plan

No database migrations required. The changes are:
1. New parser file `schwab_json.py`
2. Factory: replace `SchwabParser` with `SchwabJSONParser` for Schwab
3. New REST endpoint
4. Frontend `accept` attribute change to `.json`

**Existing Schwab CSV imports:** Any trades already imported via the CSV legacy path remain in the database untouched. They were created without `BrokerRawTransaction` rows. A fresh-start re-import with the JSON file will replace them with properly linked BRT + LogicalExecution rows. This is the recommended migration path for existing users.

Rollback: revert factory to point back to `SchwabParser`. No DB changes needed.
